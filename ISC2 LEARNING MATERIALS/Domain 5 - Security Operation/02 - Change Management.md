## Logging and Monitoring Security Events
Logging is the primary form of instrumentation that attempts to capture signals generated by events.

Logging and monitoring security events provide the operational visibility required to *detect, investigate, and respond* to unauthorized activities, system failures, and potential breaches.

>An event is defined as any action that takes place within the system environment and causes a measurable or observable change in one or more elements or resources within the system.
### Key Information Recorded and Reviewed
Logged data typically includes:
- **User IDs**
- **Device activities**
- **Configuration changes**, such as logins and logouts
- **Device and location identities**
- **Successful and repeated system and resource access attempts**
- **System configuration changes** and system protection activation and deactivation events
### Purpose of Health Monitoring
Logging and monitoring the health of the information environment are essential for identifying inefficient or improperly performing systems, detecting security compromises, and providing a chronological record of how systems are utilized.
### Robust Logging Practices and Integrity Controls
Robust logging practices provide the tools necessary to correlate information from diverse systems, allowing security teams to fully understand relationships between different activities.
- **Accountability and Review**: Logs implement security controls, provide accountability, and satisfy regulatory reviews. They are critical for uncovering security incidents, policy violations, and ensuring business continuity.
- **Tamper Protection**: Logs must be kept in an unalterable manner to preserve accountability. Organizations must implement technical controls to protect logs from unauthorized access, modification, or deletion.
- **Retention Limits**: Logs must not be kept beyond their required or useful life, aligning with data minimization and retention policies.
### Nigerian Operational Scenario
A commercial bank in Lagos configures its core transaction servers and firewalls to stream all administrator logins, configuration changes, and failed access attempts to a centralized, write-once-read-many (WORM) storage repository and SIEM. This ensures that even if an attacker or rogue system administrator compromises a local application server, they cannot modify or delete the local log files to cover their tracks, maintaining strict accountability and compliance with regulatory audit standards.

## Configuration Management Overview
Configuration management is the process and disciplined system used to ensure that only changes made to a system are those that have been authorized and validated. It prevents unmanaged modifications that could introduce security vulnerabilities, configuration drift, or system instability.
### Core Components of Configuration Management
The framework relies on four primary operational pillars:
- **Identification**: Baseline identification of a system and all its components, interfaces and documentation.
- **Baseline**: A security baseline is a minimum level of protection that can be used as a reference point. This baseline serves as a known "*good state*" against which future changes, audits, and security postures are measured.
- **Change Control**: This is an update process for requesting changes to a baseline, by means of making changes to one or more components in that baseline. A review and approval process for all changes. This includes *updates* and *patches*. This ensures that changes do not compromise security or availability. *A formal, structured workflow for requesting, reviewing, testing, approving, and documenting any modifications to production systems. This ensures that changes do not compromise security or availability.*
- **Verification and Audit**: A regression and validation process, which may involve testing and analysis, to verify that nothing in the system was broken by a newly applied set of changes. An audit process can validate that the currently in-use baseline matches the sum total of its initial baseline plus all approved changes applied in sequence.
### Supporting Elements: Inventories, Baselines, Updates, and Patches
- **Inventories**: Maintaining accurate, up-to-date asset inventories is the foundation of configuration management. It ensures that administrative teams track hardware lifecycles, software licenses, and firmware versions across the entire enterprise network.
- **Baselines**: A baseline represents the official secure configuration blueprint. For example, a bank's hardened server template ensures that unnecessary services are disabled, default passwords are changed, and strict security policies are enforced before deployment. *The baseline is a total inventory of all the system’s components, hardware, software, data, administrative controls, documentation, and user instructions.*
- **Updates**: Modifications or feature enhancements released by vendors to improve software functionality, performance, or operational efficiency, distinct from security-specific fixes.
- **Patches**: Specific, targeted code modifications designed to fix known software bugs or close security vulnerabilities. Effective patch management ensures vulnerabilities are tested and deployed rapidly to thwart active exploits.
### Nigerian Operational Scenario
A commercial bank headquartered in Lagos runs a core banking application across distributed servers in multiple branches. If an IT administrator wants to modify firewall rules or update server configurations on a live production server, configuration management and change control policies require them to submit a formal change request. The change must be reviewed by a change advisory board (CAB), tested in a staging environment, and verified against the approved security baseline before implementation. This prevents unauthorized configuration changes that could cause system outages or open security gaps.
## Change Management Components
Change management components ensure that modifications to an IT environment follow a controlled, measurable lifecycle starting from a Request for Change (RFC) to final release.
### Documentation
Every major change practice begins with an RFC (request for change) and moves through development and testing stages until release. From first to last, each step requires formalized management and decision-making, generating accounting or log entries to document every result and action taken.
### Approval
This stage involves evaluating RFCs for completeness and routing them through the proper change authorization process based on risk levels and organizational practices. It includes stakeholder reviews, identifying and allocating necessary resources, securing formal approvals or rejections, and documenting the final decision.
### Rollback
If monitoring reveals performance issues or change failure, a rollback plan defines the procedures to revert the system to its previous stable state. The lifecycle involves scheduling the change, testing it, verifying rollback procedures, implementing the change, evaluating its operation in production, and documenting the outcome. Rollback authority and timing (immediate or scheduled) are explicitly outlined in the rollback plan.
### Nigerian Operational Scenario
A digital lending platform in Lagos wants to update its core credit-scoring algorithm in production. Under change management components:
- **Documentation**: An RFC is submitted, and every development and test stage logs the code adjustments and review results.
- **Approval**: The Risk and Security committees review the RFC for completeness, verify resource allocation, and grant formal approval based on risk.
- **Rollback**: A pre-tested rollback script and plan are prepared. If monitoring detects that the new algorithm causes widespread transaction failures, the rollback procedure is executed immediately to restore system stability.
